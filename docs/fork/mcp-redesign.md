# Koharu MCP: что исправить и что переделать

Документ для агента, который будет править MCP-сервер Koharu. Он собран по итогам перевода пяти книг через этот сервер:
- «Osananajimi A to Z»;
- «Tsugi no ippo o kimi to», 92 стр.;
- «それでも君は素直になれない！», 43 стр.;
- «がんばりしだい», 40 стр.;
- «ラブミーラブユー», 38 стр.

Агент-исполнитель картинок не смотрит, поэтому каждый визуальный случай описан словами и числами: размер страницы, боксы `[x, y, w, h]` в пикселях страницы, что где нарисовано. Краткий журнал по ходу работы лежит в `mcp-improvements.md`, этот документ его заменяет и упорядочивает.

## 0. Где код и как он устроен

- **Код на `origin/main`:** транспорт MCP — `crates/koharu-app/src/commands/agent/mcp.rs`, описания и диспетчер инструментов — `.../agent/host.rs` (`fn tools`, `fn invoke`, `fn mutate`), вся логика вёрстки, проверок и измерений — `.../agent/typesetting.rs` (~4500 строк). В рабочей ветке `claude/project-thread-lbw4bo` этого кода нет: сначала переключитесь на `main` (см. правило AGENTS.md про переехавшего владельца).
- **Версия сервера в работе была чуть новее `origin/main` (c77d7eb2):** `run_pipeline` уже отвечал полем `units`. Перед правкой сверьте каждый пункт с текущим кодом.
- **Ограничения из AGENTS.md:** UI вызывает типизированные команды, без HTTP-клиента и без общего конверта событий. Agent работает со снимками и отправляет патчи, сам файлы хранилища не пишет. Обратной совместимости не добавлять: старую форму удалять. Тест добавлять только там, где он защищает реальную границу регрессии. UI-изменения подтверждать скриншотом.

### Как сервер используют на практике

Внешний агент (Claude Code по HTTP на `127.0.0.1:4100/mcp`) переводит главу. Владелец параллельно чистит её в приложении. Агенту запрещено чистить, трогать растр, запускать платные задачи и переупорядочивать страницы.

Типичный цикл по странице: `page_layers` → `crop` (compare) → правка source и перевод → `apply_layers` → `crop` для проверки. В конце: `check_chapter` (база, затем `balloons` и `lettering` по диапазонам), `hide_untranslated`, кроп каждой страницы.

**Главный практический вывод.** Агент почти не может опираться на картинки. В последних книгах больше половины запросов на просмотр кропов отбрасывались из-за лимита изображений на сессию («media removed: request limit»), и даже оставшиеся съедают контекст. Значит, всё, что сейчас проверяется только глазами, должен сообщать текст: наложения слоёв, текст поверх рисунка, неверный стиль, пропущенные реплики.

### Сколько своего кода пришлось написать

Чтобы закончить пять книг, агент написал вокруг MCP около десяти скриптов. Каждый из них — это логика, которой нет на сервере:

| Скрипт агента | Что делал | Что это значит для сервера |
|---|---|---|
| `pg.py`, `pg5.py` | Одним `apply_layers` на страницу выставляет шрифт по роли, цвет и обводку по исходнику, наклон звуков к краю и размер бокса для звуков | Нет высокоуровневой операции «сверстать страницу по правилам» |
| `sfx.py` | Словарь JP→RU для частых звуков (ビクッ→«Дёрг», ハア→«Ха-а») | Перевод — работа агента, но пропуск неочищенных звуков и их стиль можно делать на сервере |
| `grow.py`, `grow2.py` | Перебирает боксы через `preview_layers`, ищет, где кегль крупнее и нет переполнения | `auto_fit` не ищет лучший бокс и не пробует переносы |
| `bfill.py` (заливка) и `rays` (лучи) | Ищет внутренность баллона на чистом кропе, когда сервер баллон не распознал | Нет запасного измерения баллона |
| `clus.py` | Собирает обрывки `cleaned_without_text` в блоки по реплике и добавляет по ним слои | Нет восстановления слоёв по следам очистки |
| `readable.py` | Читает `readable_color` и применяет его | Нет режима «подобрать читаемый стиль» |
| `uncross.py`, `fixcross.py` | Ищет бокс, который не пересекает контур баллона | Проверка сообщает о пересечении, но не предлагает исправление |
| Пошаговое уменьшение кегля | Повторяет `apply_layers`, снижая размер на 1,5 px, пока не исчезнет overflow | Нет «максимального кегля, который влезает» с ручными переносами |

Раздел 2 предлагает перенести эту логику на сервер.

## 1. Ошибки и неудобства, по приоритету

Каждый пункт: **Симптом** (что видел агент, словами и числами) → **Причина** (если видна в коде) → **Что сделать** → **Как проверить**.

### P0. Ломает работу или искажает результат

#### 1.1 Позиционные адреса слоёв `45#13` сдвигаются после каждого изменения состава слоёв

- **Симптом.**
  - Адрес — это порядковый номер слоя в текстовой группе страницы (`typesetting::addresses`, `typesetting::address`). Любой `merge_text_layers`, `delete_elements` или `add_text_layer` перенумеровывает все слои после затронутого.
  - Сервер честно возвращает `renumbered` (`host.rs`, `fn mutate`), но агенту приходится переписывать все отложенные ссылки.
  - Реальная ошибка на стр. 39 книги «がんばりしだい». Агент добавил три слоя через `add_text_layer` подряд, а затем применил заранее подготовленный перевод выходных данных к «слою 1». Новый слой встал в порядке чтения перед старым и получил номер 1. В итоге перевод выходных данных записался в слой с комментарием автора, а настоящий слой выходных данных остался без перевода.
  - То же случалось на стр. 4, 8, 9, 10, 18, 20 разных книг при цепочке склеек: после каждой склейки номера смещались на 1–13 позиций.
- **Причина.** Адрес вычисляется из текущего порядка слоёв, стабильного короткого имени у слоя нет.
- **Что сделать (кардинально).** Дать каждому текстовому слою стабильный короткий адрес, который не меняется до удаления слоя: например `45:L7`, где `L7` — порядковый номер создания в странице (счётчик хранится в странице и не переиспользуется). Его выдают `page_layers`, `chapter_text`, `check_chapter` и все ответы правок. Позиционные `45#13` удалить целиком (правило «никакой обратной совместимости»). Порядок чтения уже отдаётся отдельным полем `reading`, номер слоя для него не нужен. `renumbered` после этого становится не нужен и удаляется.
- **Как проверить.** Тест на `typesetting::address`: добавить слой перед существующим и убедиться, что адрес существующего не изменился. Склеить два слоя: адрес первого остаётся, адрес второго перестаёт разрешаться с понятной ошибкой «слой 45:L9 удалён (склеен в 45:L7)».

#### 1.2 Одна ошибка в пачке `apply_layers` отменяет всю пачку, и непонятно, какое изменение виновато

- **Симптом.** Пачка из 20–48 изменений (вся страница) падает целиком в таких случаях:
  - неизвестное поле (`unknown field nofill … at line 1 column 1462`);
  - неверное значение перечисления (`unknown variant dev.koharu.text.sign`, `unknown variant left, expected start…`);
  - `no detected balloon holds …`;
  - `give X either a region, corners or flow balloon`.

  Ошибка разбора указывает на колонку в JSON, а не на номер изменения и слой. Агенту приходится вручную искать, какое изменение из 40 сломано.
- **Причина.** Разбор `ApplyLayers` идёт через serde целиком, а `typesetting::steps` прерывается на первой ошибке.
- **Что сделать.**
  1. Сначала проверить все изменения и вернуть список ошибок с `index` изменения, адресом слоя и полем: «change 7 (12:L3): unknown field `nofill`; allowed: element, text, …».
  2. Режим по умолчанию остаётся «всё или ничего» (одна правка — один шаг undo), но ошибка перечисляет все проблемные изменения сразу, а не первое.
  3. Конфликт `region`/`flow`/`corners` внутри одного изменения — ошибка. А «у слоя уже был `region`, пришёл `flow: balloon`» — это не конфликт: новое значение просто заменяет старое.
  4. «Нет баллона под слоем» при `flow: balloon` — ошибка только этого изменения с подсказкой «дайте region». Сейчас она молча роняет всю страницу.
- **Как проверить.** Тест на `steps`: пачка из трёх изменений, второе с неизвестной ролью. Ответ содержит `index: 1` и адрес слоя, проект не изменён.

#### 1.3 Детекция пропускает текст на некоторых книгах, и `check_chapter unboxed` этого не видит

- **Симптом (книга «がんばりしだい», 40 стр.).**
  - Страницы большие: 2447×3472. Текст набран тонким японским шрифтом в вертикальных столбцах, высота знака около 50 px.
  - Детекция нашла 70 текстовых слоёв, хотя реплик на страницах около 185. На 10 страницах слоёв не было совсем.
  - Повторный `run_pipeline detection` на этих 10 страницах вернул `completed 10 of 10` и снова ноль слоёв.
  - `check_chapter kinds: ["unboxed"]` ответил «No issues».
  - При этом в `page_layers.cleaned_without_text` были сотни мелких боксов: владелец стёр весь текст, и сервер это знал. Например, на стр. 13 — 27 боксов вроде `[299, 587, 50, 192]`, `[354, 588, 53, 94]`, по одному на кусок столбца.
  - Агент склеил эти обрывки в 114 блоков (зазор склейки 70 px), добавил по каждому слой через `add_text_layer`, прогнал `ocr local_ocr: true` — и всё прочиталось верно.
  - Для контраста: книга «ラブミーラブユー» (1200×1702, тот же автор и шрифт, но меньше разрешение) дала 210 слоёв, почти без пропусков. Похоже, детекция зависит от масштаба: на крупных страницах тонкий шрифт не ловится.
- **Причина (гипотеза).** Модель детекции работает на фиксированном входном размере, а страница 2447 px по ширине ужимается так, что тонкие столбцы теряются. `open_unboxed_text` (koharu-pipeline) ищет текст вне регионов по исходнику, а не по разнице «исходник минус чистка».
- **Что сделать.**
  1. **В детекции** (koharu-pipeline, вне MCP) для страниц шире ~1600 px запускать модель плитками с перекрытием или на двух масштабах и объединять боксы. Это правка конвейера, она требует сравнения на одинаковых входах (AGENTS.md: «A model port needs a structured comparison»). Мерило — число найденных регионов на этих 40 страницах до и после.
  2. **В MCP:** `unboxed` должен учитывать и `cleaned_without_text`. Если очистка стёрла пиксели, а текстового слоя над ними нет — это пропущенная надпись. Склеивать обрывки в блоки на сервере: сливать боксы с зазором меньше ~1,4 высоты знака по поперечной оси столбцов и отдавать блоки, а не обрывки.
  3. **Новый инструмент** (или режим `add_text_layer`): «создать слои по всем таким блокам на страницах N–M и прочитать их локальным OCR». Агент делал это вручную 114 вызовами.
- **Как проверить.** Синтетический тест: исходник — белая страница с чёрным прямоугольником-«столбцом» 50×190, чистка — белая страница, слоёв нет. `unboxed` возвращает один блок, покрывающий прямоугольник. Два столбца в 10 px друг от друга дают один блок.

#### 1.4 Баллоны не распознаются (вся книга «がんばりしだい»), и `flow: balloon` недоступен

- **Симптом.** На всех 184 слоях книги `page_layers.balloon` был пуст. Баллоны там обычные: белый овал с чёрным контуром толщиной 3–4 px на белом или тонированном фоне.
  - Агент находил их сам по чистому кропу (`crop view: clean, scale: 0.5`): заливка белого (яркость > 200) от центра бокса текста, ограничение площади 12% кадра. Внутренний прямоугольник — габарит заливки с отступом 12–17% по ширине и 10–14% по высоте, в зависимости от заполненности габарита.
  - Где заливка «протекала» (баллон открыт или нарисован без контура), использовались лучи из бокса текста в четыре стороны до первого тёмного пикселя (< 110), медиана по трём смещениям.
  - Так нашлись баллоны у всех слоёв, кроме подписей на рисунке.
- **Причина.** В `balloon_interior` (typesetting.rs) уже есть похожая заливка, но она запускается только при наличии `balloon` от детекции (`balloon: [f64;4]` — обязательный аргумент). Без бокса баллона от детектора измерение не начинается.
- **Что сделать.** Если детектор не дал баллон, запускать `balloon_interior` с затравкой из бокса текста и рамкой поиска «бокс текста × 4, не дальше границы панели». Принимать результат, только если заливка замкнута: не упёрлась в край рамки и не превысила площадь. Помечать такой баллон `measured: "fill"`, чтобы `flow: balloon` и проверки им пользовались.
- **Как проверить.** Синтетика: белая страница, чёрный эллипс 200×300 с контуром 4 px, внутри бокс текста 80×160. Без детекторного баллона `page_layers` отдаёт `balloon.inner_box` внутри эллипса. Тот же тест с разрывом контура в 30 px отдаёт `balloon: null`, а не залитую страницу.

#### 1.5 Скрытые текстовые группы невидимы, пока у слоёв нет перевода

- **Симптом (стр. 17–19 и 34, «それでも君は素直になれない！»).**
  - `inspect_project` показывал `text_layers: 18, shown: 0`.
  - `page_layers` отдавал у каждого слоя `visible: true` и `hidden_by: "text_group"`, но без id группы.
  - `check_chapter full` и `kinds: ["hidden"]` возвращали `hidden: false, hidden_by: null`.
  - `set_visibility` с id страницы ничего не делал.
  - Id группы появился в `check_chapter` только после того, как у слоёв появился перевод. Только тогда агент смог вызвать `set_visibility` с id группы.
  - В книге «Tsugi no ippo» (стр. 76–77) было то же самое. Агент дважды тратил время на расследование.
- **Причина.** В `check_chapter` (`typesetting.rs:1255`) `hidden_by` вычисляется только для «issue.hidden», а `hidden` у задачи считается только для переведённого текста. `page_layers` кладёт строку `"text_group"` без id.
- **Что сделать.**
  1. `page_layers` отдаёт `hidden_by: {"text_group": "<id>"}` всегда, когда группа скрыта.
  2. `inspect_project` на уровне страницы отдаёт `text_group_hidden: true`.
  3. `set_visibility` принимает адрес страницы как «текстовая группа этой страницы», либо появляется явная операция «показать текст страницы».
  4. `check_chapter` сообщает о скрытой группе независимо от перевода.
- **Как проверить.** Тест: скрыть группу страницы без переводов. `page_layers` отдаёт id, `check_chapter kinds: ["hidden"]` отдаёт страницу.

### P1. Сильно замедляет или требует ручной работы на каждой странице

#### 1.6 Стиль исходной надписи: тон «светлый/тёмный» вместо цвета, и советы противоречат друг другу

Сейчас в `page_layers.lettering` есть `tone`, `outline`, `check_color` и `check_outline` (`measure_lettering`, `lettering` в typesetting.rs). Это большой шаг вперёд: после жалобы владельца на белый текст без обводки на стр. 6 второй книги эти поля закрыли основную ошибку. Остались такие проблемы:

- **Цвет не передаётся.**
  - Розовый подзаголовок обложки («Мидория Изуку × Бакуго Кацуки», цвет около RGB 233,70,140) помечен `tone: light, outline: dark`, и `lettering` требует изменить цвет.
  - Жёлтое название обложки «ラブミーラブユー» (RGB ~226,214,30, зелёная обводка RGB ~30,130,120 толщиной ~10 px) агент подбирал на глаз.
  - Тон — это яркость выше или ниже 128, поэтому любой цветной текст классифицируется произвольно.
- **`readable_color` спорит с `lettering`.**
  - Белый текст на сером тоне (стр. 27–35 третьей книги, слои `27#25`, `28#26`, `29#2`, `33#9`, `35#3`) получил `low_contrast`, и `readable_color` предложил чёрный.
  - После установки чёрного `lettering` ругался: «fill opposite to source».
  - Агент в итоге оставил белый и добавил тёмную обводку 4 px, а `lettering` начал ругаться на `outline_extra`.
  - Описание говорит «или оставьте цвет и обведите», но это не выражено в данных.
- **У слоёв, где под текстом уже чисто, `tone: null`.** Так было на стр. 24, 33, 38 последней книги. Проверка стиля их пропускает, совета нет.
- **Что сделать.**
  1. Измерять и отдавать сам цвет: `source_style: { fill: [r,g,b], outline: [r,g,b] | null, outline_width_px: f }` — медиана удалённых пикселей ядра штриха и кольца. Функция `lettering` уже различает ядро и кольцо через разницу «исходник минус чистка», осталось вернуть цвет, а не порог.
  2. Сравнивать с типографией слоя по расстоянию в цвете (ΔE или хотя бы евклидово в RGB, порог ~60), а не по половине шкалы.
  3. Заменить `readable_color` одним советом `suggested_style` с полями `color`, `stroke_color`, `stroke_width`. Правило: исходный цвет сохраняется. Если он нечитаем на фоне чистки, предлагается обводка контрастного тона, а не смена цвета. `lettering` не ругается на обводку, которую советует сам сервер.
  4. Дать `apply_layers` флаг `typography: { match_source: true }`: сервер сам ставит `source_style` (и `suggested_style`, если нужно). Сейчас эту логику повторяет `pg.py` у каждого агента.
- **Как проверить.**
  - Синтетика: исходник — розовый текст RGB 233,70,140 с белой обводкой 4 px на сером фоне, чистка — серый фон. `source_style.fill` в пределах ±20 по каналам от исходника, `outline` близок к белому, ширина 3–5 px.
  - `match_source: true` выставляет эти значения, и `check_chapter kinds: ["lettering"]` молчит.

#### 1.7 `auto_fit` в узких вертикальных баллонах уменьшает кегль, а не переносит

- **Симптом.**
  - Японский текст стоит столбиком, поэтому баллоны узкие и высокие. Типичные внутренние размеры (`balloon.inner_box`, стр. 1200×1702): `[105, 862, 64, 113]`, `[108, 556, 70, 107]`, `[699, 565, 68, 134]`.
  - Русская реплика «Трахнуться хочешь?» или «Ты меня разбудил.» в такой бокс ставится с `auto_fit` кеглем 10–14 px, а `small` порог — 1,2% ширины страницы, около 14 px.
  - Вручную агент добивался 18–22 px переносами по слогам («Трах-/нуться/хочешь?», «Хоро-/шо.»).
  - Вручную проставлены переносы в 20 баллонах только последней книги, и примерно столько же в каждой предыдущей. Плюс цикл «уменьшить кегль на 1,5 px и проверить ещё раз» до трёх итераций.
- **Причина.** Описание `preview_layers` говорит, что `auto_fit` переносит «as a last resort». Порядок у раскладки сейчас такой: «уменьшить, пока не влезет, а перенос — только если слово не влезает ни при каком кегле».
- **Что сделать.** В раскладке при `auto_fit` сравнивать варианты по наибольшему кеглю:
  - а) без переносов;
  - б) с переносами по слогам в длинных словах (русские правила: не отрывать одну букву, не переносить после «ь», «ъ», «й» в начале строки и т. п.).

  Брать тот, что даёт кегль крупнее хотя бы на 10%. Для формы баллона нужен выбор «ширина строки — высота блока». Сейчас ширина фиксирована балоном на каждой высоте, а для узкого высокого баллона лучше больше коротких строк.
- **Как проверить.** Тест раскладки: бокс 70×110, текст «Ты меня разбудил.», шрифт NM Shonen 2. Кегль с переносами ≥ 18 px, без переносов ≤ 14 px. Выбран первый вариант.

#### 1.8 Медиана `balloons` считается без учёта формы, и замечания «ниже медианы» почти всегда ложные

- **Симптом.**
  - После каждой книги оставалось 27–98 замечаний «size=17.5 similar_median=21.5». Около 90% из них — узкие вертикальные баллоны, куда крупнее не влезает.
  - Агент перебирал боксы скриптом `grow.py` (десятки `preview_layers` на слой) и улучшал 10–30% таких слоёв. Остальные оставлял, а в отчёт писал одно и то же объяснение.
- **Что сделать.**
  1. Считать медиану в группе похожих баллонов: близкие площадь внутреннего бокса и пропорции ширина/высота (например, в пределах ×1,5).
  2. Замечание выдавать, только если для этого текста в этом баллоне сервер может получить кегль крупнее: проверить раскладкой с переносами из 1.7, а при успехе приложить готовый `region` и кегль.

  Так замечание становится исполнимым («можно 22 px в region [...]»), а не информационным.
- **Как проверить.** Тест: два баллона на странице, 300×200 и 70×110, оба с текстом, кегли 30 и 18 px. Замечание о втором не выдаётся.

#### 1.9 Сдвоенный баллон: две реплики ложатся друг на друга

- **Симптом.** Сдвоенный баллон — два белых овала, соединённых перемычкой, в каждом своя реплика.
  - На стр. 17 книги «がんばりしだい» верхний овал «しないよ» и нижний «おやすみかっちゃん» дали два слоя. Без `flow: balloon` (баллоны не распознаны, см. 1.4) заливка от каждого слоя нашла один и тот же общий контур, и оба перевода встали в центр общего контура поверх друг друга.
  - То же на стр. 20 (четыре реплики в трёх соединённых баллонах), стр. 28, 30, 32. Агент заметил это только на финальной сводке кропов и задал области долей вручную.
  - Описание сервера говорит, что одиночный текст в сдвоенном баллоне идёт в самую большую долю (`b6c59fb2`). Но если в одной форме два слоя, их нужно развести по долям.
- **Что сделать.**
  1. Делить форму баллона на доли по сужениям (перемычкам): например, по минимумам ширины заливки вдоль главной оси. Назначать каждому слою долю, ближайшую к его боксу детекции.
  2. Добавить в `check_chapter` вид **`overlap`**: отрисованные блоки двух видимых слоёв пересекаются больше чем на N% меньшего. Сейчас наложение никак не сообщается, и без картинок его не найти.
- **Как проверить.** Синтетика: два эллипса 150×200, соединённые перемычкой шириной 40 px. Слой A в верхнем, слой B в нижнем. После `flow: balloon` их отрисованные боксы не пересекаются. Тест `overlap`: два слоя с одинаковым регионом попадают в замечания.

#### 1.10 Надписи без баллона, но реплики, детектируются как «звуки»

- **Симптом.** Многие реплики вне баллонов детекция пометила `onomatopoeia`:
  - 気ィ付けろよ? («Ты уж поосторожнее»), 問題ねェ, 半日だってさ, 着いたよ!, クソッ;
  - る («Давай», ответ Деку крупным шрифтом), おまけ!! («Бонус»).

  Агент сам менял роль, шрифт и стиль (с d_CCShoutOut на NM Shonen 2, без наклона). При ошибке реплика получала шрифт звуков и поворот ±15°.
- **Что сделать.** Отдать эвристику роли сервера в `page_layers.role_hint`. Поле уже видно в ответе `preview_layers`, но не заполнено. Признаки реплики: в тексте есть частицы и знаки препинания, длина > 3 знаков, нет удлинителей ッー〜, обычный печатный шрифт по толщине штриха. Агенту останется подтвердить.
- **Как проверить.** Юнит-тест эвристики на списке строк выше.

#### 1.11 Мусорный OCR не помечается

- **Симптом.** Служебные страницы читаются бессмыслицей, а `ocr.confidence` у них пустой и `unverified: false`:
  - выходные данные в «ラブミーラブユー», стр. 28: строка из 500 символов вида «『ララーララララ…』(Edditerializa ipsssss iptempted ixts ixts ixts …»;
  - правила перепечатки во второй книге, стр. 2: «一緒に» повторено 80 раз;
  - послесловия.

  Агент находил их только при чтении `chapter_text`.
- **Что сделать.** Заполнить `source_suspect` (поле уже есть в схеме ответа). Признаки:
  - доля повторяющихся n-грамм выше 30%;
  - смесь латиницы и японского в одной строке без пробелов;
  - строка длиннее 300 знаков на один бокс;
  - символы вне ожидаемого письма.

  `check_chapter kinds: ["ocr"]` выводит такие слои.
- **Как проверить.** Юнит-тест детектора на двух строках выше (истина) и на обычных репликах (ложь).

#### 1.12 Нельзя пометить «не переводить намеренно» и «проверено глазами»

- **Симптом.**
  - `hide_untranslated` скрывает всё непереведённое одним вызовом, и причина нигде не сохраняется. Это могут быть неочищенный звук, англоязычная надпись, QR-код или мусор детекции.
  - При следующем проходе нельзя отличить намеренно оставленное от пропущенного.
  - В `balloons` уже появилась пометка «balloon shape partly measured: check by eye, then pass the layer in accepted». Хорошо, что есть `accepted`, но пометка живёт только в аргументах одного вызова.
- **Что сделать.** Хранимый признак слоя `keep: "original" | "not_lettering"` с короткой причиной. Его ставит агент, а `hide_untranslated` скрывает именно такие слои. Отметку «проверено» для конкретного замечания тоже хранить на слое, чтобы `check_chapter` не выдавал её снова. Хранить — в Scene, как данные текста, а не в UI (AGENTS.md: Scene владеет смыслом проекта).
- **Как проверить.** Пометить слой и пересобрать снимок: `check_chapter` его не выводит ни в `translation`, ни в `balloons`.

#### 1.13 Нет пакетной правки нескольких страниц

- **Симптом.** `apply_layers` принимает изменения любых слоёв по адресам, но ответ и проверки идут по странице. На книгу в 92 страницы уходили сотни вызовов. Отдельно `check_chapter` по диапазонам, отдельно `preview_layers` на каждый вариант бокса.
- **Что сделать.** После 1.6–1.9 большая часть этих вызовов уйдёт: сервер сам подберёт стиль и бокс. Оставшееся покрыть так:
  - `apply_layers` с `quiet: true` и изменениями по нескольким страницам — одна правка, одна запись на шаг undo;
  - `preview_layers`, который принимает несколько вариантов для одного слоя и возвращает лучший.

### P2. Неточности, которые путают

#### 1.14 Значения в разных инструментах записаны по-разному

- **Роль.** `page_layers` отдаёт `role: "dev.koharu.text.free-text"`, а `apply_layers` принимает `free_text`. Нужно одно написание во всех ответах и аргументах.
- **Выравнивание:** только `start`/`center`/`end`/`justify`. Это нормально, но ошибка должна перечислять допустимые значения, номер изменения и слой.
- **Страница:** `view_page` и `crop` берут строку `"17"`, а при числе падают с «invalid type: integer». `check_chapter.pages` — диапазон `[a, b]`, а при списке страниц ошибка выглядит как «trailing characters at line 1 column 17». Нужно одно правило: адрес страницы — строка или число в любых инструментах, `pages` — либо диапазон, либо список, но с понятной ошибкой.

#### 1.15 `preview_layers` иногда отдаёт два JSON-объекта подряд в одном текстовом блоке

- **Симптом.** Стандартный `json.loads` падает с «Extra data: line 2 column 1». Агент перешёл на `raw_decode`.
- **Что сделать.** Найти, где в ответ дописывается второй объект: вероятно, `Invocation::read(value)` вместе с отдельным блоком изображения склеиваются в один текстовый элемент. Должен быть один JSON на текстовый блок.

#### 1.16 Боксы звуков от детекции выходят за край страницы

- **Пример:** `[-81, 1163, 470, 675]`, `[697, -39, 1115, 1059]`, `[-19, 42, 226, 216]`. Агенту приходится обрезать их самому, иначе текст уходит за поле.
- **Что сделать:** обрезать регион по странице при сохранении геометрии, либо при раскладке.

#### 1.17 Конфиг шрифтов может противоречить правилам владельца

- **Симптом.** `kind_fonts.narration: "NM Scandal"`, а владелец требует, чтобы наррация шла шрифтом NM Shonen 2. Агент ставил шрифт вручную на каждом слое во всех пяти книгах.
- **Что сделать.** Это настройка владельца, не баг MCP. В инструкции сервера стоит явно сказать: при расхождении правил владельца и `kind_fonts` агент сообщает об этом в отчёте и спрашивает. Либо владелец исправляет конфиг. Дублирующий механизм переопределения в MCP добавлять не нужно.

#### 1.18 `run_pipeline detection` на всей книге работает 5,5 минут без признаков жизни

- **Симптом.** 38 страниц: детекция 332 с, OCR 190 с. Ответ приходит только в конце, промежуточного прогресса нет. Клиент агента при этом молчит, и пользователь дважды спрашивал «что ты делаешь 8 минут?».
- **Что сделать.** Отправлять MCP progress notifications (`notifications/progress`) с числом готовых страниц. В `run_pipeline` уже есть `progress: None` в `koharu_pipeline::Request`, подключить его к MCP. Нового вида задачи и второго пути отмены не добавлять: AGENTS.md запрещает дублировать операцию.

#### 1.19 Ловушка с локальным scope при подключении

- **Симптом.** `claude mcp add`, запущенный из `C:\WINDOWS\system32`, зарегистрировал сервер только для этой папки, и в проекте инструментов не было. Агент потерял время на HTTP-обход.
- **Что сделать:** в документации подключения указать `--scope user` или запуск из папки проекта.

## 2. Что переделать кардинально

### 2.1 Высокоуровневая операция «сверстать слой по правилам» вместо ручной типографики

Сейчас агент сам решает для каждого слоя:
- шрифт по роли;
- цвет и обводку по исходнику;
- наклон звука к краю страницы (±15°, никогда не 90°);
- бокс звука (вокруг исходного или рядом с неочищенным);
- `flow: balloon` или свой бокс;
- кегль, одинаковый для похожих баллонов страницы;
- переносы.

Всё это детерминированные правила. Они уже записаны в инструкции сервера, и каждый агент переписывает их скриптом заново. Ошибки в этих скриптах и есть основная масса проблем, на которые жаловался владелец.

**Предложение.** `apply_layers` принимает у изменения `style: "auto"`. Тогда сервер:
1. выбирает шрифт по роли из `kind_fonts`;
2. ставит `source_style`, а если нечитаемо — `suggested_style` (1.6);
3. для текста в баллоне ставит `flow: balloon` с делением долей (1.9), иначе бокс из детекции, обрезанный по странице (1.16);
4. для звука, который ещё нарисован (`left: kept`), ставит бокс рядом с ним, не поверх, в сторону края страницы, с наклоном ±15° к краю;
5. подбирает кегль раскладкой с переносами (1.7) и выравнивает похожие баллоны страницы к общему кеглю, если он влезает во все;
6. возвращает итог одной строкой на слой и предупреждения.

Агент передаёт только текст и, при необходимости, исключения. Ручные поля типографики остаются для исключений.

### 2.2 Текстовые проверки всего, что сейчас видно только на картинке

Агент не может просматривать кропы постоянно (лимит изображений). Поэтому проверки должны покрывать то, что сейчас ловится только глазами:

| Что агент ловил глазами | Текстовая проверка |
|---|---|
| Два перевода друг на друге (сдвоенные баллоны) | `overlap`: пересечение отрисованных блоков видимых слоёв (1.9) |
| Текст поверх рисунка в баллоне, перекрытом рисунком (стр. 18, 20, 25 третьей книги) | `over_art`: доля тёмных пикселей чистки под отрисованными глифами выше порога |
| Реплика, которую детекция не нашла (стр. 11 последней книги, «う» в маленьком баллоне) | `unboxed` по следам очистки (1.3) и `empty_balloons` для баллонов, найденных заливкой (1.4) |
| Текст обрезан полем страницы или уходит за панель | `clipped`: отрисованный блок выходит за страницу или за измеренную панель |
| Неверный стиль на фоне (белый на белом) | Уже есть `low_contrast`, но совет должен быть один (1.6) |

Каждое замечание должно нести готовое исправление (region, size, style), где сервер может его вычислить.

### 2.3 Стабильная модель адресов и замечаний

Вместе с 1.1 и 1.12: у слоя стабильный адрес, хранимые пометки (`keep`, `accepted` по виду замечания), а `check_chapter` отдаёт только замечания, по которым нужно действовать. Тогда финальный проход сводится к «пусто — готово», а не к чтению сотни строк с одним и тем же объяснением в отчёте.

### 2.4 Запасные пути, когда модели не справились

Детектор текста и детектор баллонов иногда отказывают целиком (1.3, 1.4). Сервер уже владеет нужными данными:
- исходник и чистка — значит, известны стёртые пиксели;
- функция `balloon_interior` с заливкой.

Нужно включать запасной путь автоматически и помечать результат (`measured: "fill"`, `source: "cleaned"`), а не оставлять агента с пустыми полями.
