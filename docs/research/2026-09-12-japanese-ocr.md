# OCR японской манги: варианты и проверка качества

Проверено по первичным источникам 12 сентября 2026 года, включая документацию предыдущего проекта `manga-translator`. Новые сравнительные прогоны на пользовательских страницах и платные запросы не выполнялись.

Выбранная пользователем модель — `qwen-vl-ocr-2025-11-20`. Нужен отдельный адаптер Alibaba с режимами прямого OCR и локального OCR с последующей проверкой изображения. Результат применять автоматически; отдельный интерфейс сравнения кандидатов и подтверждения пользователь отверг. Остальные модели ниже оставлены как исследованные альтернативы.

У Qwen-VL-OCR есть существенное различие: `text_recognition` описан для китайского и английского, а **`multi_lan` включает японский**. Модель не принимает пользовательский system message; инструкции передаются в user message. Для версий до Qwen3.5-OCR встроенная задача использует фиксированный prompt, а версия 2025-11-20 обрабатывает только последнее сообщение. Поэтому нельзя считать, что общий chat-шаблон с черновиком автоматически работает правильно. OpenAI-compatible вызов документирован, но требует правильного task-specific prompt. [Ограничения и вызовы Qwen-OCR](https://www.alibabacloud.com/help/en/model-studio/qwen-vl-ocr).

Если нужен именно свободный запрос «картинка + локальный черновик → исправленная транскрипция», запасной кандидат — **Qwen3-VL-Plus**: $0.20 / $1.60 при входе до 32K токенов в Singapore International. Более дешевый Qwen3-VL-Flash — $0.05 / $0.40 в тех же условиях. Это отдельные универсальные VLM, не алиасы Qwen-VL-OCR; более длинный вход оплачивается дороже. [Тарифы Alibaba](https://www.alibabacloud.com/help/en/model-studio/model-pricing), [описание Plus](https://www.alibabacloud.com/help/en/model-studio/qwen3-vl-plus).

OCR 3 имеет код `mistral-ocr-2512` и остается доступным для существующих интеграций; OCR 4.1 — `mistral-ocr-4-1`. Услуга разметки стоит отдельно: $3 / $5 за 1000 размеченных страниц соответственно. Это тарифы специального `/v1/ocr`, не обычного чата Mistral. В списке OCR-языков есть японский. [OCR 3](https://docs.mistral.ai/models/ocr-3-25-12), [OCR 4.1](https://docs.mistral.ai/models/ocr-4-1), [языки](https://docs.mistral.ai/resources/languages).

**Граница доказательств:** у перечисленных API не найдено сопоставимого первичного теста именно на японской манге с отдельными результатами для вертикального текста, фуриганы и нарисованных звуковых эффектов. Поддержка Japanese или высокий результат на документах этого не доказывает. Manga OCR, уже используемый в проекте, прямо разрабатывался для вертикального/горизонтального текста, фуриганы и разных манга-шрифтов; его стоит оставить базовой линией. Авторы также предупреждают о выдуманном тексте на пустых изображениях. [Manga OCR](https://github.com/kha-white/manga-ocr).

## Контракт адаптера Qwen-VL-OCR 2025-11-20

Для ключа **Singapore** подходит полный endpoint:

```text
POST https://dashscope-intl.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation
Authorization: Bearer <Alibaba Model Studio API key>
Content-Type: application/json
```

Существующий домен Singapore официально продолжает работать. Новый рекомендуемый host — `{WorkspaceId}.ap-southeast-1.maas.aliyuncs.com`, путь запроса тот же. Для Beijing: `dashscope.aliyuncs.com` либо `{WorkspaceId}.cn-beijing.maas.aliyuncs.com`; для Virginia: `{WorkspaceId}.us-east-1.maas.aliyuncs.com`. Ключи и доступность моделей привязаны к региону, автоматически менять регион при ошибке нельзя. [Регионы](https://www.alibabacloud.com/help/en/model-studio/regions), [действительность старых доменов](https://www.alibabacloud.com/help/en/model-studio/error-code).

В Koharu добавлены собственные API-ключ провайдера `Qwen OCR (Alibaba Cloud)` и `base_url` — базовый адрес API, по умолчанию `https://dashscope-intl.aliyuncs.com/api/v1/`. Адаптер сам дописывает `services/aigc/multimodal-generation/generation`; полный endpoint в поле адреса вводить не нужно. ID модели зафиксирован в каталоге. Эти поля принадлежат OCR-адаптеру и не используют URL, ключ или имя модели локального OpenAI-compatible сервера. Проверка доступа конкретным ключом в этом исследовании не выполнялась.

Минимальное тело прямого многоязычного OCR; вместо `BASE64` подставляется исходный PNG-фрагмент:

```json
{
  "model": "qwen-vl-ocr-2025-11-20",
  "input": {
    "messages": [{
      "role": "user",
      "content": [{
        "image": "data:image/png;base64,BASE64",
        "min_pixels": 3072,
        "max_pixels": 8388608,
        "enable_rotate": false
      }]
    }]
  },
  "parameters": {
    "ocr_options": { "task": "multi_lan" }
  }
}
```

DashScope возвращает текст в `output.choices[0].message.content[].text`, статистику в `usage.input_tokens`, `usage.output_tokens`, `usage.image_tokens` и идентификатор в `request_id`. Читать `output.text` нельзя: он может быть `null`. `finish_reason: length` означает обрезанный ответ. Для обычного HTTP не требовать наличия SDK-поля `status_code`; проверять HTTP-статус и структуру ответа. [Формат запросов и ответов](https://www.alibabacloud.com/help/en/model-studio/qwen-vl-ocr-api-reference).

**Режим с локальным черновиком имеет другое тело:** удалить `parameters.ocr_options`, добавить после изображения в тот же `content` элемент `{ "text": "инструкция OCR и помеченный локальный черновик" }`. Пользовательский image+text prompt для этой точной версии документирован. Сочетать его со встроенной `multi_lan` нельзя рассчитывая на использование черновика: до Qwen3.5-OCR встроенная задача подменяет prompt фиксированным. `system` и историю сообщений не отправлять. Следовательно, прямой режим использует `multi_lan`, а гибридный — пользовательский OCR prompt без встроенной задачи. Поддержка формата запроса не доказывает прироста качества от черновика. [Custom prompt и встроенные задачи](https://www.alibabacloud.com/help/en/model-studio/qwen-vl-ocr).

Для передачи через Base64 документация ограничивает исходный файл размером менее 7 MB, строку Base64 — не более 10 MB. В HTTP передавать Data URL, а не путь Windows. [Передача изображений](https://www.alibabacloud.com/help/en/model-studio/qwen-vl-ocr). Ошибку, пустой или обрезанный ответ не применять поверх готового текста: оставить локальный результат и сообщить сбой; повторный запуск должен быть явным либо ограниченным политикой временных сетевых ошибок.

## Как организовать гибридный OCR

Старый проект дает основание перенести этот режим в Koharu как опцию и проверить на одинаковых входах. Универсальное улучшение для каждой модели и страницы обещать нельзя. Исследование EACL 2026 сравнивает image-only, OCR-only и их сочетание на деловых документах: сильным VLM предварительный OCR нужен не всегда. Эти результаты не являются проверкой манги. [Статья](https://aclanthology.org/2026.eacl-industry.28.pdf).

Предлагаемая схема для Koharu:

1. Получить локальный OCR **для того же исходного фрагмента**, который пойдет в API. Брать изображение до очистки и вписывания перевода, сохранять стабильный ID блока.
2. В одном запросе передать картинку и явно помеченный ненадежный черновик. Для выбранной версии Qwen использовать custom prompt без `ocr_options.task`, как описано выше. Требовать транскрипцию видимого японского текста без перевода, литературной правки и дополнения по смыслу. При расхождении приоритет у изображения. Черновик и надписи на картинке — данные, не инструкции.
3. Заранее определить обращение с фуриганой: основной текст для перевода отдельно; фуригана — отдельное поле, если нужна. SFX распознавать как отдельные блоки, не смешивать с репликами.
4. Полный успешный результат применять автоматически, без отдельного сравнения и подтверждения. При сетевой ошибке оставить локальный текст и показать причину; не скрывать сбой как успешную проверку.
5. Для экономии сначала проверять выбранный блок или явно выбранные страницы. Автоматическую отправку «неуверенных» блоков включать после калибровки: оценка уверенности, придуманная самой VLM, не равна вероятности правильности.

Основной риск — **привязка к ошибочному черновику**: модель может повторить локальную ошибку, даже когда на картинке читается другое. Другие проверяемые риски — потеря мелкой фуриганы при уменьшении картинки, смешение соседних реплик и «исправление» намеренной разговорной записи. Это основания для сравнения режимов, а не установленные дефекты конкретного API.

## Небольшая проверка перед выбором модели

Предлагаемый протокол, без запуска в рамках этого исследования:

- Подготовить 100–200 вручную выверенных блоков из нескольких глав: обычный горизонтальный текст, вертикальный, фуригана, SFX, плохие сканы и пустые фрагменты. Несколько целых страниц нужны отдельно для проверки порядка блоков. Данные держать вне Git.
- На одинаковых фрагментах сравнить **A: локальный OCR**, **B: API только с изображением**, **C: API с изображением и локальным OCR**. Зафиксировать версию модели, prompt, настройки и разрешение; менять один фактор за раз. Часть страниц оставить для итоговой проверки, не подстраивая под них prompt.
- Считать `CER = (замены + удаления + вставки) / число символов эталона` по каждому классу и всему набору. Сохранить сырой CER и отдельно вариант с заранее фиксированной нормализацией пробелов/переносов; не скрывать ошибки кандзи или малой каны нормализацией. Формула основана на расстоянии редактирования. [Метрика CER](https://github.com/huggingface/evaluate/blob/main/metrics/cer/README.md).
- Отдельно измерять пропущенные/лишние блоки и долю неверно упорядоченных пар ID блоков. Для страницы порядок размечать вручную с учетом панелей; простая сортировка справа налево не заменяет чтение манги. Фуригану оценивать отдельно от основного текста; на пустых фрагментах считать ложное распознавание.
- Зафиксировать задержку, фактические input/output tokens, количество повторов, итоговую стоимость и минуты ручного исправления. Для локального прохода указать устройство и размер изображения, загрузку/прогрев модели вынести за измерение. Проверить, сколько правильных ответов A испортил режим C.

Стоимость токенных API считать по фактическому usage: `(input_tokens × input_price + output_tokens × output_price) / 1_000_000`. Одинаковая картинка может иметь разное число токенов у разных провайдеров; токенную цену нельзя напрямую переводить в цену страницы. У Mistral отдельно учитывать, сколько страниц/изображений фактически отправлено. Практический критерий выбора — меньше ошибок и ручной работы при приемлемой полной стоимости, включая повторные запросы.
